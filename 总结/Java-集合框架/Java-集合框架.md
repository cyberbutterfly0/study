## 概念卡

### Map 与 key（先弄清「凭什么找得到」）

- 是什么: `Map` 是键值容器，`put(k, v)` 存、`get(k)` 按 key 取回。
- 为什么: 用 String 当 key 不会出问题，因为 String 自己定义好了"怎么算相同"；换成自己写的类，这份定义就得你自己给。
- 关键机制: 先不展开，等学到"重写方法"再补——那才是这个示例真正要讲的一课。
- 我的理解偏差: 还没到这个阶段。
- 待验证: 等学到重写方法后，再回来做「只重写 equals / 只重写 hashCode」两个失败的实验。现在不用做。

### 重写 equals 与 hashCode（暂缓：等学到重写方法再看）

- 是什么: `equals` 判定「两个对象是否相等」，`hashCode` 给出「这个对象大概属于哪一组（桶）」。HashMap 靠 `hashCode` 找到桶、再在桶内用 `equals` 逐个比对。
- 为什么: 不重写就等于用 `Object` 的默认实现——默认 `equals` 是引用比较、默认 `hashCode` 是身份哈希。于是「内容相同的两个对象」既进不了同一个桶，也不会被判为相等，`get` 自然取不到 `put` 进去的值。
- 关键机制: 契约只有两条——`equals` 返回 true 的两个对象，`hashCode` 必须相等；`hashCode` 相等的对象，`equals` 不一定相等（哈希冲突）。所以重写 `equals` 就必须重写 `hashCode`。
- 最小示例:
  - 只重写 `equals`：两个内容相同的 key 进不同桶，`get` 返回 null。
  - 只重写 `hashCode`：进了同一个桶，但桶内 `equals` 仍不相等，`get` 还是 null。
- 我的理解偏差: 一开始以为「值一样就能取到」，把 `==`、`equals`、`hashCode` 三者的职责混在一起了——`==` 比引用，`equals` 比内容，`hashCode` 只负责分桶。
- 待验证: 自己写一个只有 `id` 字段的类，分别制造上面两种失败，把两次 `get` 的返回值打出来。

### HashMap 的扩容与负载因子

- 是什么: 元素数超过 `容量 × 负载因子`（默认 0.75）时，容量翻倍并把已有元素重新分桶。
- 为什么: 桶太满会让桶内链表/红黑树变长，查找从近似 O(1) 退化。
- 关键机制: 扩容会重算每个元素的下标，顺序不保证；这就是 HashMap 不保证迭代顺序的原因。
- 我的理解偏差: 无（还没细问）

## 易错点

- **症状**：`map.put(k1, v)` 之后 `map.get(k2)` 返回 null，而 `k1.equals(k2)` 是 true。**原因**：只重写了 `equals`，两者的 `hashCode` 不同，被分到不同桶。**做法**：两个一起重写，且 `equals` 里用到的字段全部参与 `hashCode` 计算。
- **症状**：用可变对象（如放进 map 后又改了字段）当 key，之后就取不到。**原因**：改字段把 `hashCode` 改了，对象留在旧桶里，新下标找不到它。**做法**：map 的 key 用不可变对象。
- **症状**：`Integer` 缓存导致 `==` 有时为 true 有时为 false。**原因**：`-128..127` 有缓存复用。**做法**：包装类型比较一律用 `equals`。
