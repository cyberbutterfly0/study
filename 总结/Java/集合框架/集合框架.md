## 概览

示例情境：用户问「HashMap 里为什么有时候取不到刚放进去的值」——真实原因是自定义 key 没同时重写 `equals` 和 `hashCode`。但用户当前**还没学到重写方法**，所以这一轮只停在「Map 是什么、key 靠什么找」这一层，不给判定链的细节。

- 能用 `Map<String, Integer>` 做 put / get，key 用 String 或 Integer 这类现成类型。
- 懂基本语法：变量、方法调用、`new`。

## 概念卡

### Map 与 key（先弄清「凭什么找得到」）

- 是什么: `Map` 是键值容器，`put(k, v)` 存、`get(k)` 按 key 取回。
- 为什么: 用 String 当 key 不会出问题，因为 String 自己定义好了"怎么算相同"；换成自己写的类，这份定义就得你自己给。
- 关键机制: 先不展开，等学到"重写方法"再补——那才是这个示例真正要讲的一课。
- 我的理解偏差: 还没到这个阶段。
- 待验证: 等学到重写方法后，再回来做「只重写 equals / 只重写 hashCode」两个失败的实验。现在不用做。

### 重写 equals 与 hashCode（暂缓：等学到重写方法再看）

- 是什么: `equals` 判定「两个对象是否相等」，`hashCode` 给出「这个对象大概属于哪一组（桶）」。HashMap 靠 `hashCode` 找到桶、再在桶内用 `equals` 逐个比对。
- 为什么: 不重写就等于用 `Object` 的默认实现——默认 `equals` 是引用比较、默认 `hashCode` 是身份哈希。于是「内容相同的两个对象」既进不了同一个桶，也不会被判为相等，`get` 自然取不到 `put` 进去的值。
- 关键机制: 契约只有两条——`equals` 返回 true 的两个对象，`hashCode` 必须相等；`hashCode` 相等的对象，`equals` 不一定相等（哈希冲突）。所以重写 `equals` 就必须重写 `hashCode`。
- 最小示例:
  - 只重写 `equals`：两个内容相同的 key 进不同桶，`get` 返回 null。
  - 只重写 `hashCode`：进了同一个桶，但桶内 `equals` 仍不相等，`get` 还是 null。
- 我的理解偏差: 一开始以为「值一样就能取到」，把 `==`、`equals`、`hashCode` 三者的职责混在一起了——`==` 比引用，`equals` 比内容，`hashCode` 只负责分桶。
- 待验证: 自己写一个只有 `id` 字段的类，分别制造上面两种失败，把两次 `get` 的返回值打出来。

### HashMap 的扩容与负载因子

- 是什么: 元素数超过 `容量 × 负载因子`（默认 0.75）时，容量翻倍并把已有元素重新分桶。
- 为什么: 桶太满会让桶内链表/红黑树变长，查找从近似 O(1) 退化。
- 关键机制: 扩容会重算每个元素的下标，顺序不保证；这就是 HashMap 不保证迭代顺序的原因。
- 我的理解偏差: 无（还没细问）

## 易错点

- **症状**：`map.put(k1, v)` 之后 `map.get(k2)` 返回 null，而 `k1.equals(k2)` 是 true。**原因**：只重写了 `equals`，两者的 `hashCode` 不同，被分到不同桶。**做法**：两个一起重写，且 `equals` 里用到的字段全部参与 `hashCode` 计算。
- **症状**：用可变对象（如放进 map 后又改了字段）当 key，之后就取不到。**原因**：改字段把 `hashCode` 改了，对象留在旧桶里，新下标找不到它。**做法**：map 的 key 用不可变对象。
- **症状**：`Integer` 缓存导致 `==` 有时为 true 有时为 false。**原因**：`-128..127` 有缓存复用。**做法**：包装类型比较一律用 `equals`。

**选择题**

1. 自己写了个 `User` 类，只重写了 `equals`、没重写 `hashCode`。用两个 `id` 相同的 `User` 对象当 key：`map.put(u1, "A")` 之后 `map.get(u2)` 返回什么？
   - A. `"A"`，因为 `u1.equals(u2)` 是 true
   - B. `null`，因为两者的 hashCode 不同，被分到了不同的桶
   - C. 抛 `NullPointerException`
   - D. 编译报错，自定义对象不能当 key
   - 答案: B
   - 判定: B。HashMap 的查找分两步：先用 `hashCode` 算下标定位桶，再在桶内用 `equals` 逐个比对。只重写 `equals`，`hashCode` 还是 `Object` 的身份哈希（两个对象不同），进的是不同桶，压根走不到 `equals` 那一步。A 把"能被判相等"当成了"能被找到"。C 错，找不到就返回 null，不抛异常。D 错，任何对象都能当 key，语法上完全合法。
   - 踩坑场景: 单元测试里 `u1.equals(u2)` 打印出 true，就笃定 map 一定能取到，结果线上一直返回 null，查了半天以为是 map 的 bug。

   **术语**

   | 术语 | 含义 | 通俗解释 |
   |---|---|---|
   | hashCode | 对象的一个整数指纹，决定它进哪个桶 | 按指纹分信箱 |
   | 桶（bucket） | HashMap 内部数组的每个格子，存 hash 冲突的元素 | 一个信箱格 |
   | 身份哈希 | `Object` 默认的 hashCode，按内存地址算，两个不同对象必不同 | 按"你是谁"发号码，不是按"你长什么样" |

2. 反过来，只重写 `hashCode`、不重写 `equals`，两个 `id` 相同的对象当 key，`get` 仍然返回 null。为什么？
   - A. hashCode 冲突了，HashMap 会丢弃后放进去的那个
   - B. 两个对象进了同一个桶，但桶内比对用的 `equals` 还是引用比较，判为不相等
   - C. hashCode 必须唯一，重复就直接抛异常
   - D. Map 不允许 key 重复，后放的会覆盖前面的
   - 答案: B
   - 判定: B。重写 hashCode 只解决了"分到同一个桶"，桶内还得靠 `equals` 认亲。没重写 `equals` 就用 `Object` 的引用比较，两个对象不是同一个引用 → 不相等 → 找不到。A 错，hash 冲突是常态，HashMap 用链表或红黑树挂起来，不会丢数据。C 错，hashCode 完全允许重复。D 错，key 重复时覆盖的是"同一个 key"的值，这里两个对象根本没被判成同一个 key。
   - 踩坑场景: 以为"撞到同一个桶就等于相等"，只补了 hashCode 就以为修好了，`get` 还是 null。

   **术语**

   | 术语 | 含义 | 通俗解释 |
   |---|---|---|
   | 哈希冲突 | 两个不同对象算出同一个 hashCode | 两个人指纹撞了 |
   | 链表法 | 同一个桶里用链表串起冲突元素 | 挤一个信箱的那串人排队 |
   | equals 契约 | `equals` 返回 true 的两个对象，hashCode 必须相等 | 说是一家人，指纹也得一样 |

3. 拿一个（已重写 `equals` 与 `hashCode` 的）对象当 key 放进了 HashMap，之后改了它参与 hash 计算的那个字段，再拿同一个对象 `get`，结果？
   - A. 还是能取到，毕竟对象没换
   - B. 返回 null，对象还躺在旧桶里，按新 hash 去别的桶找当然没有
   - C. 抛 `ConcurrentModificationException`
   - D. HashMap 会自动重新分桶，能取到
   - 答案: B
   - 判定: B。改字段不会通知 map，元素仍挂在旧桶；`get` 一开始就用当前 hashCode 定位，指向了另一个桶，连 `equals` 都不会比。A 错在以为"同一个引用"就够了——定位不到就是不到。C 是遍历集合过程中改集合才抛的，跟改 key 的字段无关。D 错，重新分桶只在扩容（put 触发）时发生，HashMap 不会监听字段变化。
   - 踩坑场景: 拿自己写的实体类当 key，中途改了它的属性，之后 get 全是 null，还怀疑是不是并发问题。

   **术语**

   | 术语 | 含义 | 通俗解释 |
   |---|---|---|
   | 可变对象 | 创建后字段还能被修改的对象 | 会变形的东西 |
   | 重新分桶 | 扩容时按新容量重算每个元素的下标 | 换大柜子后重新排信箱 |

4. `Integer a = 127, b = 127;` 时 `a == b` 为 true，换成 128 就变成 false。原因是？
   - A. 127 是特殊值，编译器做了常量折叠
   - B. Integer 对 `-128..127` 有缓存池，这个范围内自动装箱会复用同一个对象
   - C. 128 超出了 int 的取值范围
   - D. 这是 JVM 的已知 bug
   - 答案: B
   - 判定: B。`Integer.valueOf` 在 `-128..127` 区间返回缓存里的同一个实例，所以 `==` 比引用为 true；超出范围每次 `new` 一个新对象，引用不同就为 false。A 错，跟 127 这个数本身没关系，边界是范围。C 错，`int` 能到 21 亿多。D 错，这是 Java 语言规范要求的行为，不是 bug。
   - 踩坑场景: 用 `==` 比 Integer，测试数据都在 127 以内全过，线上一上量全部 false。

   **术语**

   | 术语 | 含义 | 通俗解释 |
   |---|---|---|
   | 自动装箱 | 把 `int` 自动转成 `Integer` 对象 | 基本款自动包成礼盒 |
   | 缓存池 | Integer 预先创建并复用的一批对象 | 常备的几种礼盒反复用 |
   | 引用比较 | `==` 比较两个变量是不是同一个对象 | 看是不是同一个盒子，不是比盒里装的东西 |
