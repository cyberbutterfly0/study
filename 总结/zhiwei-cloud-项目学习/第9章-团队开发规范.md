## 一、开发命名说明

### 为什么在命名上花时间

好代码应该保持整洁。需求变化、排期紧不是托词，保持代码持续整洁优雅是每个开发者应遵守的原则。

### 1. 使用英语

英语是编程的主要语言，避免拼音甚至中文命名。

| 正例 | 反例 |
|---|---|
| `const firstName = 'Gustavo'` | `primerNombre` |
| `const friends = ['Kate', 'John']` | `penyou` |

### 2. 命名风格——Java 代码用 camelCase

统一小驼峰，团队内不要混用风格。

| 正例 | 反例 |
|---|---|
| `pageCount` | `page_count` |
| `shouldUpdate` | `should_update` |

### 3. 遵守 SID 原则

- **S**hort 简短——但不能简写到失去意义
- **I**ntuitive 直观——接近自然语言
- **D**escriptive 描述性——有效反映作用/目的

| 正例 | 反例 |
|---|---|
| `postCount` | `a` |
| `hasPagination` | `isPaginatable` |
| `shouldPaginate` | `shouldPaginatize`（组合动词） |

### 4. 避免过度简写

- 正例：`onItemClick`
- 反例：`onItmClk`

### 5. 避免上下文重复

`class MenuItem` 里面用 `handleClick`，不要 `handleMenuItemClick`——类名已经说明了上下文。

## 二、代码质量要求

前言：坚持简单的原则有助于提高代码的可维护性；可维护性不是开发完成后才考虑的，而是开发一开始就要考虑。

### 开发代码规范

附了《开发手册-阿里云 嵩山版.pdf》（1.5 MB），代码规范以那个 PDF 为准。

### 除代码规范外的质量要求（27 条）

1. 代码要干净整洁且逻辑清晰明了、逻辑严谨。`NullPointerException` 这种异常一定程度上能体现代码逻辑严谨程度。
2. 不要一个方法干到底。代码做到逻辑职责单一、层次分明，一个方法/类只专注一件事。
3. 不要引入莫名其妙的、出处不明的三方依赖。尽可能少引入个人贡献的开源包——要么各种漏洞，要么后期维护没保障，遇到问题坑人坑己。
4. 不要过度设计。不要「将来可能要用 xxx 现在就加上」，99% 将来用不到。
5. 不要不设计。不要只做「码砖」小能手。写业务逻辑、定义接口时考虑周全、留余地，不要每次调整逻辑都像重写。定义接口要替调用者考虑：接口就是隐藏复杂业务、提供简单友好的出口。
6. 不要为了方便而方便。代码尽量做到用到什么写什么。例如 lombok 注解不要一味 `@Data`（含 getter/setter/toString/equals/hashCode/无参构造），用不到就别用，选 `@Getter`/`@Setter` 即可——过度使用会增大代码量、浪费资源。
7. 经常重构自己的代码：删掉过时不用的业务代码、重构逻辑等。
8. 类和函数应短小，更短小。类和函数都不应过长（**函数长度最好不超过 80 行**），过长可读性一定差，往往包含大量重复代码。
9. 只做一件事（同一层次的事）。同一个函数的每条执行语句应是统一层次的抽象。例如一个函数要做「给 DTO 赋值 → 调接口 → 处理结果」三步，如果里面还包含 DTO 赋值的具体操作，就说明层次不统一。
10. 参数越少越好。参数越多调用越麻烦，尽量足够少，最好没有。
11. 别给糟糕的代码加注释，重构它。注释不能美化糟糕的代码；想加注释前先考虑能否通过调整结构、命名消除必要性。
12. 好的注释提供信息、表达意图、阐释、警告。注释容易与代码逻辑脱节（代码改了注释没跟），所以注释最好提供代码没有的额外信息、展示设计意图，而不是写具体如何实现。
13. 错误处理很重要，但也不能搞乱代码逻辑。错误处理应集中在同一层，错误处理函数最好不包含其他业务逻辑代码，只处理错误信息。
14. 抛异常时提供足够多的环境和说明，方便排查。最好把执行的类名、关键数据、环境信息都抛出；自定义异常类就派上用场了，通过统一的一层处理异常可快速定位。
15. 特例模型（Null Object）可消除异常控制或 `null` 判断。大多数异常来源于 NPE，有时可用 Null Object 消除。
16. 尽量不要返回 `null`，不要传 `null` 参数。目的是尽量降低 NPE 可能性。
17. **禁止使用 `BeanUtils.copyProperties`**。稍不留意就有坑：类型不匹配、名称大小写、性能问题、boolean 类型里 `is` 开头的属性等。
18. 写代码时把所有 `private` 写在 `public` 之下。公共接口在前、私有方法在后，更容易理解执行流程。
19. 所有根上的数据库更新、删除需强制做判空操作，防止传入数据为空时更新整张表；查询也需加上条件（如 `limit 1000`），防止一次取出大量数据拖死数据库或服务器。
20. 原则上禁止在循环中去取数据库。如 `for` 下面包含取数据库操作，一定需要使用请在注释上写明原因。
21. 使用大而全的接口需注意（非强制）。如 `List<CommonExtField> getList(CommonExtField commonExtField)` 这类接口确实方便，但隐患很大：容易让上层一次性获取全部数据，返回数据过大时拖死整个服务且不易查出问题。
22. 所有提交的代码通过 IDEA 默认的格式化代码清理一次。这样可以减少合并冲突，也能清理无效的 import。
23. 前后端约定：交互时间使用**毫秒（Long 类型）**、金额单位使用**「分」**统一传输；其他字段交互尽量使用小单位以提升精度、避免精度误差。
24. 不要直接调用各类 JSON 工具（如 fastjson 的 `JSONArray`、`JSONObject`），统一使用 `YdmapJson` 工具类做序列化与解析，以便后续可方便替换 JSON 库（如 fastjson → jackson）。
25. `JSON_CONTAINS` 参数使用 `validSalesIds->'$'` 可命中 JSON 数组索引，例如：`JSON_CONTAINS(validSalesIds->'$', '105205')` 或 `105205 MEMBER OF (validSalesIds->'$')`。
26. 输出错误日志时不能只打印 `e.getMessage()`——无法定位具体出错行。必须用 `log.error("**异常", e)` 或 `log.error("***异常：{}", e.getMessage(), e)`，确保日志含完整异常堆栈。
27. 为避免逻辑隐藏的潜在缺陷，项目中原则上**禁止使用三元运算符（`?:`）**。

## 三、团队文化（基础信息）

### 快速融入团队指引

> 原文开头：为了大家能够有一个愉快的共事环境，分享一下我们团队做人做事的一些原则，当无人给你指引时请按以下方式做决定并执行。

**用心做事**

- 以「作为人何为正确」为判断标准进行抉择执行——不考虑利害关系、不考虑难度，只问自己这样做对不对。能力可以随着时间和努力程度逐步提升，但做选择和决定却由人的性格及利害关系等因素决定。
- 以一颗「耐烦」的心来做事。任何事情想做好都会有让你心烦气躁的时候；今天烦了可以停下，过后继续改进。

**以「又好又快」来做产品**

- 一件事「做完」和「做好」有本质区别。作为自研团队，产品研发以「又好又快」为目标——在保证质量的前提下提升效率，而不是只求交付、不重质量的外包式做法。

**理清因果关系，多想，多问为什么（多反思，多改进）**

- 少讲大道理，求实落实，把问题追问清楚：我们要解决什么问题？为什么会出现这个问题？这个问题可以分解为几个次级问题？如何解决？需要什么资源？潜在困难有哪些？
- 客户提这个需求背后的想法是什么、为了达到什么目的？产品为什么要这样设计、代码为什么要这样写？
- 多问为什么同样适用于改掉自身毛病：为什么我不能早起？为什么我比别人差一点？为什么我做事半途而废？

**为队友考虑，人人为我，我为人人**

- 客观看待队友意见，从长远角度分析是否有好处；如果是，请接受，不要因难度较大或与自己意见相左而拒绝改进。
- 队友因失误出问题时，请扶一把——你也会有失误的时候。

**多维度提升自己，形成统一气质**

- 一个人一种气质，一个团队也一样。希望大家多提升自我，形成主动担当、迎难而上的气质。
- 提升顺序：**人格能力 > 通用能力 > 专业能力**（先有主动担当的意愿才会去推动事情，为了完成具体事情才会有学专业知识的动力）。
  - 人格能力：基础品德、主动担当、迎难而上
  - 通用能力：多人合作、沟通能力、事情推动能力
  - 专业能力：代码水平、新技术学习能力

### 高效工作及团队配合

**现阶段的目标**

为各类 O2O 行业提高整体运营效率、实现产业互联。当前集中在文体行业；未来会拓展到酒店、民宿、美业、医疗（康复治疗、运动医学、体检）、展览、培训活动、露营等各类「线上预约 + 线下履约」场景。

**产品的特点**

为客户提供软件服务，按时长（1 年或多年）收费，即客户租用软件服务。客户下一次续费或是否加大使用力度，很大程度上反映我们的产品和服务做得好不好。

**工作的特点**

现阶段以任务为驱动的协作方式：每个人的任务分工并不完全确定，也没有复杂的流程管理；需要时立即组合，任务完成后自动解散；任何人都可以担任某个任务的 Leader。

**做事的风格**

1. 坦诚地交流、就事论事地讨论问题。
2. 如果一项改动对长远有利，立即改动（如果因为当前项目进度或其他原因暂未按原方案执行，过后应启动下一版本改进）。

**工作方式建议（9 条）**

1. 为好的系统架构做持续改进及「斗争」——好架构能在项目越大、功能越多时仍保持高效产出和系统稳定性。功能点大多由业务同学提出，但评估系统架构的重要性和紧急程度是研发人员的职责；业务提功能后如需改架构，先把结构调整完再补功能，别做别扭的功能给后续留隐患。
2. 有好想法和建议就提出来，不论是否本职范围内（对公司、对产品、对技术方案、流程等）；没被采用也会给出原因。
3. 功能较大时拆成多个小模块分步上线——缩小上线波动范围、提高对完成时间的控制。
4. 研发同学避免闭门造车，要和真实用户及使用者（也含内部同事）站在一起感受系统设计，最终解决痛点；切勿等需求只管实现。
5. 过去成功的经验或已成功的产品可参考，但不要绝对化，根据当前实际来解决问题。
6. 对待需求要了解清楚背后的原因，如果有更优想法请提出来。
7. 明白「积羽沉舟」的道理——好产品由各种细节组成，看到可优化空间就即时优化。
8. 做事要明确目标和资源（人员、时间等）的投入产出比；允许对未来有好处的长远投入，但要预估、明确和关注——本质是成本思维。
9. 在保证质量的情况下想尽一切办法提升效率（每天思考是否有成倍增长效率的可能），无论是工作本身的效率、为使用者提高效率，还是提高生活效率。
