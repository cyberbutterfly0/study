# 第5章 框架层代码

框架层在 `zhiwei-framework`，核心是 `zhiwei-common` 和 `zhiwei-spring-boot-starter-web`、`zhiwei-spring-boot-starter-security`。下面这些是所有业务模块都要用的。

## 一、Ret<T> — 统一响应体

所有 Controller 都返回 `Ret<T>`：

```json
{
  "httpCode": 200,
  "code": 0,
  "msg": null,
  "data": "...",
  "requestId": "a1b2c3...",
  "timestamp": 1690000000000
}
```

| 字段 | 含义 |
|---|---|
| `httpCode` | HTTP 状态码（200/400/401/403/500），用 `ResponseEntity` 保证响应头一致 |
| `code` | 业务错误码，0 = 成功，1xxx = 业务异常 |
| `msg` | 提示文案 |
| `requestId` | 从 MDC 取 traceId，日志和响应能对上号 |
| `timestamp` | 服务端时间戳 |

静态工厂方法：

```java
Ret.ok()                     // 成功，无数据
Ret.ok(data)                 // 成功，带数据
Ret.ok(msg, data)            // 成功，自定义提示
Ret.error(httpCode, code, msg)  // 失败
```

## 二、ErrorCode — 错误码枚举

| 枚举 | 码 | 含义 |
|---|---|---|
| `SUCCESS` | 0 | 成功 |
| `BAD_REQUEST` | 400 | 参数错误 |
| `UNAUTHORIZED` | 401 | 未认证 |
| `FORBIDDEN` | 403 | 无权限 |
| `NOT_FOUND` | 404 | 不存在 |
| `INTERNAL_ERROR` | 500 | 服务内部错误 |
| `USER_NOT_FOUND` | 1001 | 用户不存在（业务码） |
| `USER_PASSWORD_ERROR` | 1002 | 密码错误（业务码） |
| `TENANT_NOT_FOUND` | 1003 | 租户不存在（业务码） |

每个枚举值带 `msgKey`（如 `error.bad_request`），实际文案由 i18n 资源文件提供。

## 三、Args — 业务参数校验

`zhiwei-common/src/main/java/cloud/zhiwei/common/Args.java`，`public final class Args`，11-04 的 `aeb54d1` 加进来。

```java
Args.notNull(user, "user");                 // 抛 ServiceException(BAD_REQUEST, "error.param_required", "user")
Args.notBlank(username, "username");
Args.notEmpty(ids, "ids");                  // Collection
Args.notEmpty(paramMap, "paramMap");        // Map
Args.validId(orgId, "orgId");               // 必须 > 0
Args.isTrue(count > 0, "error.xxx");        // 条件不成立就抛
```

为什么不用别的：

| 做法 | 问题 |
|---|---|
| `Objects.requireNonNull(x)` | 抛 NPE，被兜底成 500，前端看到「服务器错误」 |
| Spring `Assert` | 抛 `IllegalArgumentException`，也是 500 |
| 只靠 `@Valid` | 只覆盖 Controller 入口；Service 被定时任务、MQ、Feign 调用时没有校验 |

抛出的异常 message 都是 i18n key：`Args.PARAM_REQUIRED_KEY = "error.param_required"`，字段名放 `args`，由全局异常处理器翻译成「参数 user 不能为空」。

## 四、ServiceException — 业务异常

```java
throw new ServiceException(ErrorCode.USER_NOT_FOUND);
throw new ServiceException(ErrorCode.BAD_REQUEST, "error.param_required", "username");
```

11-06 的 `e46262a` 加了两样东西：

- **`Object[] args` 占位符**：message 里可以带 `{}`，配合 i18n 参数
- **按 ErrorCode 推导 HTTP 码**：`HTTP 语义码（4xx/5xx）直接用，业务码 1xxx 映射成 400`

几个构造：

| 构造 | 用途 |
|---|---|
| `(ErrorCode)` | 最常见，code + 默认 msgKey |
| `(ErrorCode, String messageKey, Object... args)` | 自定义 key + 占位符参数 |
| `(Integer httpCode, Integer code, String message, Object[] args)` | 全指定 |
| `(Integer code, String message, Object... args)` | 默认 HTTP 400 |

`message` 存的是 **i18n key**，不是最终文案，由全局异常处理器翻译。

## 五、GlobalExceptionHandler — 全局异常处理

`@RestControllerAdvice`，11-06 补齐后覆盖这些：

| 异常 | HTTP 码 | 处理 |
|---|---|---|
| `ServiceException` | 看异常里的 httpCode | 业务异常；message 是 `error.param_required` 时把 `args[0]` 用 `MessageUtils.resolveFieldName` 翻成字段中文名 |
| `MethodArgumentNotValidException` / `BindException` | 400 | `@Valid` 校验失败，拼字段错误 |
| `HttpRequestMethodNotSupportedException` | 405 | 方法不对（新增） |
| `HttpMessageNotReadableException` 等 | 400 | 请求体解析失败（新增） |
| `MaxUploadSizeExceededException` | 413 | 上传超限（新增） |
| `DistributedLockException` | 409 / 1001 | 分布式锁冲突（新增） |
| `Exception` | 500 | 兜底，打完整堆栈，**不泄露内部信息**给前端 |

两个实现细节值得记：

- **上传大小从配置读**：`@Value("${spring.servlet.multipart.max-file-size:1MB}")` 解析成 `DataSize`，不靠 `getMaxUploadSize()`——Tomcat 的 `SizeLimitExceededException` 经 Spring 转换后这个方法返回 `-1`，直接换算会显示成「不能超过 0MB」
- **日志只记 code 不记 message**：message 可能带手机号、身份证，进日志就等于泄露。需要定位时按 code + traceId 回查

## 六、TraceIdFilter + LogTraceUtil — 链路追踪

- `TraceIdFilter` 是优先级最高的 Servlet Filter（`Integer.MIN_VALUE`）
- 优先读请求头 `X-Trace-Id`（跨服务传递），没有就生成 UUID 前 16 位
- 放进 MDC，日志自动带 `[traceId]`；`Ret` 响应体也带 `requestId`
- `finally` 里清理 MDC，**防止线程池复用串号**

## 七、MessageUtils + I18nConfig — 国际化

- `basename=i18n/messages`，自动匹配 `messages.properties`（英文默认）和 `messages_zh_CN.properties`（中文）
- `AcceptHeaderLocaleResolver` 按请求头 `Accept-Language` 切换，默认简体中文
- 用法：`MessageUtils.get("error.bad_request")`
- 找不到 key 时**返回 key 本身**，不会抛异常

## 八、操作日志 — 拦截器 + Writer 两条腿

11-06 的 `e46262a` / `0c007a6` / `1957731` 把操作日志做成了框架能力，分成「采集」和「落库」两半：

```text
请求进来
  → OperateLogInterceptor.preHandle：记下开始时间（放 request attribute）
  → 业务方法执行
  → OperateLogInterceptor.afterCompletion：
       判断是否 POST + @PostMapping
       → 是：组装 OperateLogRecord（谁、什么时候、哪个模块、成功/失败、耗时）
       → 交给本服务实现的 OperateLogWriter 落库
```

**采集侧**（`zhiwei-spring-boot-starter-security` 的 `log/` 包）：

- `OperateLogInterceptor`（257 行，`HandlerInterceptor`）——只记 `HTTP POST` 且方法带 `@PostMapping`；`GET` 一律不记，否则列表查询瞬间把日志表撑爆
- **不记请求体/响应体**：里面可能有密码、手机号；要追溯具体数据去业务表自己的历史记录里查
- 开始时间存在 request attribute `zhiwei.operateLog.startTime`，**不放成员变量**——拦截器是单例，多请求共用实例会互相覆盖把耗时算错
- 不用 AOP 的原因：要额外引 `spring-boot-starter-aop`；而且 `afterCompletion` 在请求线程内执行，此时 `SecurityUtils` 还能取到登录用户，换成 `@Async` 就丢了

**落库侧**（各服务各写一个 Writer，实现 `OperateLogWriter.write(OperateLogRecord)`）：

| 服务 | 实现 | 方式 |
|---|---|---|
| system | `SystemOperateLogWriter`（54 行） | 转实体，走 `OperateLogService` |
| infra | `InfraOperateLogWriter`（72 行） | 直接用 `JdbcTemplate` INSERT 同一张 `sys_operate_log` |

约定写在接口注释里：**Writer 实现不抛异常、不加业务事务**，写日志失败不能影响主业务。

**自动装配**（`config/OperateLogAutoConfiguration`）：`ObjectProvider<OperateLogWriter>.getIfAvailable()` 取不到就不注册拦截器。所以引了 security starter 但没提供 Writer 的服务（比如纯查询的网关）功能降级、服务照常启动，不会因为缺 Bean 直接起不来。

## 十、这几个东西怎么串起来

```text
请求进来
  → TraceIdFilter 生成 traceId 放进 MDC
  → JwtAuthenticationTokenFilter 有 Token 就解析并写 SecurityContext，没 Token 直接放行
  → SecurityFilterChain 判路径：白名单 permitAll，其余 authenticated
  → Controller 返回值包成 Ret<T>
  → 参数校验：Controller 用 @Valid，Service 用 Args（抛 ServiceException）
  → 出异常时 GlobalExceptionHandler 拦截，翻 i18n 文案（含字段名），包成 Ret
  → 写操作额外走 OperateLogInterceptor，结束后交给 OperateLogWriter 落库
  → 响应体带上 requestId
日志里同一 traceId，能拼出完整链路
```

## 十一、安全链 — SecurityAutoConfiguration

`zhiwei-spring-boot-starter-security` 里的 `config/SecurityAutoConfiguration.java`（228 行），加了这个 starter 就自动生效：

```java
@AutoConfiguration
@ConditionalOnClass({JwtUtils.class, CacheUtils.class})
@EnableWebSecurity
```

**过滤链 `securityFilterChain(HttpSecurity)` 干了六件事**：

1. `csrf(disable)` — REST API 用 Header 传 Token，不走 Cookie，没有 CSRF 前提
2. `sessionCreationPolicy(STATELESS)` — JWT 自包含，服务端不存 Session
3. `authorizeHttpRequests` — 白名单见下，其余 `anyRequest().authenticated()`
4. `formLogin(disable)`、`httpBasic(disable)` — 登录走 `/api/auth/login` 的 JSON 接口
5. `addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)`
6. 白名单路径：
   - `/api/auth/login`
   - `/api/auth/get-user-info`、`/api/auth/get-menus`（**故意放行**：让 Controller 在未登录时抛 401，前端才能区分「未登录」和「无权限」；直接拦会变 403，前端分不出来）
   - `/api/system/health`、`/api/infra/health`、`/api/auth/health`
   - `/v3/api-docs/**`、`/doc.html`、`/webjars/**`

**没写自定义 `AuthenticationEntryPoint` / `AccessDeniedHandler`**（全仓库 grep 无结果），所以受保护接口未登录时走 Spring Security 默认行为 = **403**；401 只来自业务代码抛 `ErrorCode.UNAUTHORIZED`。

**`@EnableMethodSecurity` 没开**（类注释：等 RBAC 权限体系完整再启用），所以现在没有 `@PreAuthorize`，权限判断靠 URL 级 + Service 里手工校验。

**JWT 密钥是硬编码默认值，没被任何配置覆盖**：

```java
@Value("${zhiwei.security.jwt.secret:zhiwei-cloud-default-secret-key-change-in-production!!}")
private String jwtSecret;
```

三个服务的 12 个 `application*.yml` 里 grep `jwt` / `security` / `secret` 全部无命中，Nacos 里的 dev 配置也是空的 → 实际跑的就是这一串默认值。仓库公开，等于**任何人都能自己签一个合法 token**。生产必须通过环境变量或 Nacos 覆盖（见坑 #20）。
